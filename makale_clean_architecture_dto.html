REST API Tasarımında Clean Architecture, DTO Pattern ve @RestControllerAdvice İle Global Exception Handling

Spring Boot projelerinde katmanlı mimari ilkeleri, veri izolasyonu ve sürdürülebilir hata yönetimi standartları.

Ahmet Furkan Kısacık

Spring Boot ile kurumsal veya bireysel bir REST API projesine başlarken en sık yapılan iki kritik hata vardır:

  1. Veritabanı tablolarımızı temsil eden @Entity sınıflarımızı doğrudan istemciye (React, Next.js, Mobile) yanıt olarak dönmek.
  2. Servislerde oluşan hataları (Örn: Kullanıcı bulunamadı, Bakiye yetersiz) Controller katmanında try-catch blokları arasına hapsedip kod kirliliği yaratmak.
"İyi bir mimari; sadece sistem çalışırken değil, sistemde beklenmedik bir hata oluştuğunda bile istemciye ne olduğunu anlaşılır ve standart bir dilde söyleyebilen mimaridir."

Bu makalede, katmanlı mimari prensiplerini koruyarak DTO (Data Transfer Object) desenini ve @RestControllerAdvice ile merkezi hata yönetimini adım adım kuracağız.

1. Veritabanı Entity'lerini Neden Dışarıya Açmamalıyız?

Bir @Entity sınıfını Controller uç noktasından yanıt olarak döndüğümüzde şu 3 temel riskle karşılaşırız:

  • Güvenlik Zafiyeti (Data Leakage & Over-Posting): Kullanıcının passwordHash, tckn veya failedLoginCount gibi verileri dış dünyaya sızar.
  • Sonsuz Döngü (Circular Dependency): JPA ilişkilerinde Jackson kütüphanesi JSON dönüştürürken StackOverflowError fırlatır.
  • Gevşek Bağlantı İhlali: Veritabanında bir kolonun adını değiştirdiğiniz an istemcinin kullandığı API sözleşmesi kırılır.

❌ Kötü Pratik (Bad Practice):

@GetMapping("/{id}")
public UserEntity getUserById(@PathVariable Long id) {
    return userRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("Kullanıcı bulunamadı"));
}

✅ İyi Pratik (Clean Code):

@GetMapping("/{id}")
public ResponseEntity<UserResponseDto> getUserById(@PathVariable Long id) {
    UserResponseDto userDto = userService.getUserDtoById(id);
    return ResponseEntity.ok(userDto);
}

2. DTO ve Java Record İle Temiz Veri Akışı

DTO katmanı sayesinde sadece dış dünyanın görmesi gereken alanları paketleriz. Java 17 ile gelen record yapısı değiştirilemez (immutable) veri taşıyıcısı sunar:

public record UserResponseDto(
    Long id,
    String firstName,
    String lastName,
    String email,
    String role
) {}

3. @RestControllerAdvice İle Merkezi Hata Yönetimi

Spring Boot bize tüm Controller katmanını dinleyen AOP tabanlı @RestControllerAdvice ve @ExceptionHandler anotasyonlarını sunar.

Standart Hata Yanıt Şemamız (ErrorDetails):

public record ErrorDetails(
    LocalDateTime timestamp,
    int status,
    String error,
    String message,
    String path
) {}

Central Global Exception Handler Sınıfı:

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorDetails> handleResourceNotFoundException(
            ResourceNotFoundException ex, HttpServletRequest request) {
        
        ErrorDetails error = new ErrorDetails(
                LocalDateTime.now(),
                HttpStatus.NOT_FOUND.value(),
                "RESOURCE_NOT_FOUND",
                ex.getMessage(),
                request.getRequestURI()
        );
        return new ResponseEntity<>(error, HttpStatus.NOT_FOUND);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, String>> handleValidationExceptions(
            MethodArgumentNotValidException ex) {
        
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(err -> 
            errors.put(err.getField(), err.getDefaultMessage())
        );
        return new ResponseEntity<>(errors, HttpStatus.BAD_REQUEST);
    }
}

4. Eğitmen Gözünden: En Sık Yapılan 3 Mimarisel Hata

  1. HTTP Status 200 Dönüp İçi Hata Formatlı JSON Vermek: HTTP 200 OK verip body içinde error dönmek anti-pattern'dir.
  2. Generic Exception Fırlatmak: Her yerde RuntimeException atmak yerine domain exception sınıfları kullanılmalıdır.
  3. Hassas Sistem Detayı Sızdırmak: Stack trace ve SQL sorgularını 500 hatalarında dışarı sızdırmamak gerekir.
