Günümüz modern ve yüksek trafikli sistemlerinde monolitik (tek parça) mimariler, servislerin birbirine sıkı sıkıya bağlı (tightly coupled) olması ve eşzamanlı (synchronous) senkron çağrıların getirdiği gecikmeler (latency) nedeniyle yetersiz kalmaktadır.

Bu rehber makalemizde, gerçek hayat kurumsal senaryolarında sıklıkla kullanılan CloudVault-Security mimarisini inceleyeceğiz. Sistemimiz şu temel bileşenlerden oluşmaktadır:

  • api-gateway (Port: 8080): Spring Cloud Gateway (WebFlux) ile reaktif yönlendirme ve oran sınırlama (Rate Limiting).
  • auth-service (Port: 8081): Spring Security 6 & JJWT 0.12.5 tabanlı OAuth2 Authorization Server (Access & Refresh Token Rotasyonu).
  • vault-event-service (Port: 8082): Apache Kafka tabanlı asenkron olay üretimi (Producer) ve tüketimi (Consumer).
  • Resiliency & Fault Tolerance: Otomatik tekrar deneme (Exponential Backoff Retry) ve işlenemeyen mesajların karantinaya alındığı Dead Letter Queue (DLQ) yapısı.
"İyi bir mimari; sadece sistem çalışırken değil, sistemde beklenmedik bir hata veya ağ kesintisi oluştuğunda bile mesaj kaybını sıfıra indirebilen mimaridir."

1. Spring Kafka Producer (Olay Üretici)

Bir olay tetiklendiğinde (örneğin dosya yüklendiğinde), KafkaTemplate vasıtasıyla mesaj Kafka başlığına (topic) asenkron olarak iletilir:

✅ Spring Kafka Producer Konfigürasyonu: 
@Component
public class VaultEventProducer {

    private static final Logger log = LoggerFactory.getLogger(VaultEventProducer.class);
    private final KafkaTemplate<String, FileVaultEvent> kafkaTemplate;

    public VaultEventProducer(KafkaTemplate<String, FileVaultEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public CompletableFuture<SendResult<String, FileVaultEvent>> sendEvent(String topic, FileVaultEvent event) {
        log.info("Publishing FileVaultEvent to Kafka topic [{}]: EventID={}, FileID={}",
                topic, event.getEventId(), event.getFileId());

        CompletableFuture<SendResult<String, FileVaultEvent>> future = kafkaTemplate.send(topic, event.getFileId(), event);

        future.whenComplete((result, ex) -> {
            if (ex == null) {
                log.info("Event successfully sent to topic [{}] partition [{}] at offset [{}]",
                        topic, result.getRecordMetadata().partition(), result.getRecordMetadata().offset());
            } else {
                log.error("Failed to send Event [{}] to topic [{}]: {}", event.getEventId(), topic, ex.getMessage());
            }
        });

        return future;
    }
}

2. Hata Toleransı: Retry & Dead Letter Queue (DLQ) Konfigürasyonu

Mülakatların ve kurumsal mimarilerin en kritik konusu: "Tüketici (Consumer) tarafında bir veritabanı kesintisi veya hata yaşanırsa mesaja ne olur?"

Spring Kafka'da DefaultErrorHandler ve DeadLetterPublishingRecoverer kullanarak belirli sayıda tekrar deneme yapıp, ardından mesajı karantina başlığına (file-vault-events.DLQ) yönlendiriyoruz:

✅ Retry & DLQ Recovery Konfigürasyonu: 
@Configuration
public class KafkaConfig {

    @Bean
    public DefaultErrorHandler errorHandler(KafkaTemplate<String, FileVaultEvent> kafkaTemplate) {
        DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(kafkaTemplate,
                (record, ex) -> {
                    log.error("Retries exhausted for record in topic [{}] partition [{}] offset [{}]. Routing to DLQ...",
                            record.topic(), record.partition(), record.offset());
                    return new TopicPartition("file-vault-events.DLQ", 0);
                });

        // 3 kere dene, her deneme arasında 1000ms bekle
        FixedBackOff backOff = new FixedBackOff(1000L, 2L);
        DefaultErrorHandler errorHandler = new DefaultErrorHandler(recoverer, backOff);

        errorHandler.setRetryListeners((record, ex, deliveryAttempt) ->
                log.warn("Retry attempt #{} failed for Event ID [{}] in topic [{}]: {}",
                        deliveryAttempt, record.key(), record.topic(), ex.getMessage())
        );

        return errorHandler;
    }
}

3. DLQ Karantina Tüketicisi (DlqConsumer)

DLQ konusuna düşen hatalı mesajlar, sistem yöneticilerine alarm göndermek veya manuel inceleme için DlqConsumer bileşeni tarafından yakalanır:

✅ DLQ Listener: 
@Component
public class DlqConsumer {

    private static final Logger log = LoggerFactory.getLogger(DlqConsumer.class);

    @KafkaListener(topics = "file-vault-events.DLQ", groupId = "cloudvault-dlq-group")
    public void consumeDlq(FileVaultEvent event) {
        log.warn("🚨 ALERT: Received event in Dead Letter Queue (DLQ)! EventID={}, FileID={}, Filename={}",
                event.getEventId(), event.getFileId(), event.getFilename());
        // Manuel inceleme, veritabanına kayıt veya Slack/Email alarmı tetikleme
    }
}

💡 Bir Eğitmen ve Yazılım Mühendisinin Gözünden Tavsiyeler

100'den fazla öğrenciye yazılım mimarisi eğitimi vermiş bir eğitmen ve aktif sahada kod geliştiren bir mühendis olarak, Event-Driven mikroservis dünyasına adım atan meslektaşlarıma şu altın tavsiyeleri vermek isterim:

  • Idempotency (Yinelemesiz İşleme) Hayati Önem Taşır: Kafka'da varsayılan olarak "At-Least-Once Delivery" garantisi bulunur. Production ortamlarında tüketicilerinizi (Consumer) mutlaka eventId kontrolü ile Idempotent tasarlayın.
  • Dead Letter Queue (DLQ) Bir Çöp Kovası Değildir: Orası sisteminizin Karantina Merkezidir. DLQ konusuna mesaj düştüğünde ekibinize anında bildirim gönderen (Slack/PagerDuty) bir izleme altyapısı kurun.
  • Mülakatlarda "Neden Kafka?" Sorusuna Doğru Yanıt Verin: Mülakatlarda sadece "Çok hızlı olduğu için" demek yerine "Mikroservisler arasındaki bağımlılığı sıfıra indirmek, asenkron yük dengelemesi sağlamak ve Retry/DLQ ile veri kaybını önlemek için" yanıtını verin.
  • Sadece Kod Yazmayın, Orkestrasyona da Hakim Olun: Sisteminizin bağımlılıklarını docker-compose.yml ile tek komutta ayağa kaldırabilecek seviyede Konteyner hakimiyetine sahip olun.
